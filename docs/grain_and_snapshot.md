# Grain and Snapshot Definition

## Purpose
This markdown defines analytical grain and snapshot logic for the KKBox churn early-warning system. These decisions are foundational and must remain stable across feature engineering and modelling phases.
Feature logic, labels, and scoring are intentionally excluded.

## Business Decision
- Decision support: Weekly identification of users at risk of churn
- Decision cadence: Weekly
- Decision action: Proactive retention intervention
- Snapshot timing must align with operational workflow

## Analytical Grain Definition
- Analytical grain is one row per user per week.
- Each row represents the system's view of a user as of the **snapshot date** for that week
- No table in the analytics layer may violate this grain (no duplicates)

## Snapshot Date Definition
- Snapshot date: is defined as the week_end_date (Sunday)
- All features must be computed using data with event dates less than or equal to the **snapshot date**
- No future information beyond snapshot date is permitted

## Calendar and Week Logic
- A calendar spine table is created (dim.dim_calendar)
- Fields included are:
    - week_id
    - week_start_date
    - week_end_date
    - snapshot_date
    - iso_year
    - iso_week
- Weeks are generated independently from the user activity

## User-week Spine Construction
- A user-week spine (intermediate.int_user_week) is generated by combining:
    - unique users (msno) from the system
    - the calendar weeks during the user is considered active or observable (snapshot_date >= first_seen_date)
- The spine defines the authoritative row set for downstream joins
- All feature tables must left join onto this spine

## Logic Rules
- All source data is evaluated as-of the snapshot date
- For event-based tables (transactions, user logs):
    - only records with event dates less than or equal to snapshot date maybe used
- Latest always means latest as of snapshot date, not latest overall.

## Lookback Window Definition
- Standard lookback windows used acros the system:
    - 7 days
    - 30 days
    - 90 days
- Windows are defined relative to snapshot date
- Window boundaries are inclusive

## Known Constraints and Trade-offs
- Near-real-time scoring is out of scope
- Backfilled historical corrections are not reprocessed automatically
- Weekly cadence trades responsiveness for stability

## Validation Rules
- One row per user per week must hold
- Snapshot date must never precede feature event dates
- Row counts should grow predictably over time

## What is enabled next
- Safe feature engineering in Feature Engineering Phase
- Reliable label alignment
- Reproducible weekly scoring
